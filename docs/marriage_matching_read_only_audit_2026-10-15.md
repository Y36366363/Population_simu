# 成家匹配阶段只读成本拆分 · 2026-10-15

本轮没有新的外部历史数据，因此继续遵守 feature freeze，不增加机制，也不修改生产成家匹配循环。目标仅是回答：在 2026-10-14 的年龄窗口索引之后，剩余成本主要来自同户/近亲过滤，还是权重计算？

## 1. 诊断设计

新增的 `matching_diagnostics.py` 在模拟检查点上读取未婚男女和既有家庭关系，依次干跑：

1. 年龄窗口后的未配对状态过滤；
2. 同一家庭过滤；
3. 共享母亲过滤；
4. 共享父亲过滤；
5. 原公式的匹配权重计算。

诊断不调用 `world.rng`，不打乱、不选择配偶、不写入人员或家庭。顺序拆分会产生临时列表，因此计时只适合比较这些干跑阶段的相对成本，不能等同于生产 `_form_family_branches` 的真实总耗时。检查点也不能复现同一年度内较早成功配对导致的后续动态移除。

正式运行采用四国主情景、seed `20261006`、`20261007`、`20261008`，每个 seed 同时推进未诊断对照世界和诊断世界50年，并在第25年和第50年各重复11次干跑计时。原始结果见 [`matching_read_only_cost_profile_2026-10-15.json`](artifacts/matching_read_only_cost_profile_2026-10-15.json)，机器汇总见 [`matching_read_only_cost_summary_2026-10-15.json`](artifacts/matching_read_only_cost_summary_2026-10-15.json)。

生产文件 `family_world.py` SHA-256 仍为 `48786db8d46fcc6b7048dc3b2fb43857a57c52f0c73e9b67a33ab8eb6a48dfc9`，与10月14日接受版本完全相同。

## 2. 只读性和逐年等价

- 三个 seed × 50 年，共150个诊断/对照年度完整 fingerprint 全部一致；
- 六次检查点审计的审计前后完整 fingerprint 全部一致；
- 六次审计的 RNG 状态全部一致；
- 诊断计时不参与验收门槛。

因此，今天的工具只观察当前状态，没有改变候选顺序、权重顺序、随机调用、账本或后续轨迹。

## 3. 候选数量和实际剔除

下表报告三个 seed 的中位数。第25年对应情景年份1995，第50年对应2020。

| 指标 | 1995检查点 | 2020检查点 |
|---|---:|---:|
| 未婚女性 | 463 | 319 |
| 未婚男性 | 414 | 293 |
| 年龄窗口候选对 | 53,842 | 24,792 |
| 最终计算权重的候选对 | 53,654 | 24,729 |
| 同户剔除数 / 比例 | 125 / 0.222% | 41 / 0.159% |
| 共享母亲剔除数 / 比例 | 47 / 0.082% | 11 / 0.043% |
| 共享父亲剔除数 / 比例 | 0 / 0.000% | 1 / 0.005% |

年龄窗口已经排除了大部分显然不可能的组合；在剩余候选中，同户和近亲规则实际剔除的比例很低。不过低剔除率不等于规则没有意义：它们是家庭结构约束，不能为了性能删除。

检查点的男性池在建立时已经排除当时的已配对者，所以只读干跑中的 `active_filter` 不会剔除候选。生产年度中较早成功配对的男性仍会由同一条件从后续女性候选中排除；该动态过程没有被这份检查点统计冒充为零成本。

## 4. 成本归因

| 干跑阶段 | 1995中位耗时 | 1995阶段占比 | 2020中位耗时 | 2020阶段占比 |
|---|---:|---:|---:|---:|
| 已配对状态过滤 | 1.478 ms | 4.58% | 0.593 ms | 4.26% |
| 同户过滤 | 1.307 ms | 4.06% | 0.524 ms | 3.79% |
| 母系近亲过滤 | 3.426 ms | 10.71% | 1.468 ms | 10.68% |
| 父系近亲过滤 | 3.241 ms | 10.05% | 1.347 ms | 9.99% |
| 权重计算 | 22.771 ms | 70.63% | 9.818 ms | 71.40% |

权重计算在两个检查点都稳定占约七成，单位候选约398—401 ns。母系与父系检查合计约20.7%，同户过滤约4%。绝对耗时在第50年下降，是因为当时进入匹配池的未婚成年人及候选对更少；这不是算法复杂度自然改善的证据。

## 5. 决策

今天不修改权重公式，也不把两个亲缘判断合并进缓存。原因是：

- 权重阶段虽最大，但涉及浮点运算顺序、权重列表顺序和 `rng.choices` 输入，风险最高；
- 亲缘规则剔除率低，但属于模型有效性约束，而非可删除的冗余；
- 昨日优化后整个成家阶段只占总 step 的一部分，继续微调的整体收益上限有限；
- 当前更重要的项目瓶颈仍是外部历史验证数据，而非内部运行速度。

若未来仍需工程优化，只能先增加更细的只读、按国家和候选规模归因；任何生产改动仍需重新建立修改前基线，并通过多 seed、逐年完整 fingerprint、RNG和候选/权重顺序完全一致。取得新的外部历史数据后，应优先恢复正式验证。
